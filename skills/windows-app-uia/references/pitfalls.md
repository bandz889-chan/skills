# 막히기 쉬운 곳 (Windows)

앱마다 다르게 나올 수 있으니 "이럴 수 있다"로 읽고, 덤프 · 실제 확인으로 직접 본다.

## 1. UIA 트리가 비어 있다 (직접 그린 화면)

**증상**: 창 아래 Pane 하나뿐이고 목록 항목 · 말풍선이 안 보인다. 게임 엔진 · 자체 UI 라이브러리로 그린 앱에서 흔하다.

**대응**: Win32 모드로 창 클래스를 본다. 입력창은 표준 `Edit` · `RICHEDIT50W`인 경우가 많다.
목록 내용은 앱의 **복사 · 내보내기 · 인쇄** 같은 기능이 텍스트를 내주는지 본다
(예: 카카오톡 PC는 대화 목록에 Ctrl+A, Ctrl+C가 `[이름] [시각] 본문` 텍스트를 준다).

## 2. `WM_SETTEXT`로 값은 들어갔는데 앱이 모른다

**증상**: 검색창에 글자가 보이는데 결과가 걸러지지 않는다. 앱이 키 입력 · `EN_CHANGE` 알림을 듣고 있어서다.

**대응**: 넣은 뒤 0.3~0.6초 기다리고, Enter 키 메시지로 확정한다. 그래도 안 되면 UIA `ValuePattern.SetValue()`를 시험한다.
바로 읽으면 이전 결과가 나올 수 있다(앱의 디바운스).

## 3. Ctrl 조합 키가 안 먹는다

**증상**: `PostMessage`로 Ctrl+A를 보냈는데 'a'만 들어가거나 아무 일도 없다. 앱은 메시지 처리 시점에
`GetKeyState(VK_CONTROL)`을 보는데, 게시한 메시지에는 그 상태가 없다.

**대응**: `AttachThreadInput(내 스레드, 대상 스레드, True)` → `SetKeyboardState`로 Ctrl을 눌린 상태로 → 키 메시지 게시 →
잠깐 대기 → 원래 상태 복원 → 분리. 복사가 실제로 됐는지는 클립보드 순번으로 확인한다. 안 되면 `copy_not_observed`로 멈춘다.

## 4. 관리자 권한 앱에 아무것도 안 된다

**증상**: 오류 없이 무시된다. **대응**: [permissions.md](permissions.md)의 UIPI. 대상 앱을 일반 권한으로 다시 띄운다.

## 5. 창을 앞으로 못 가져온다

`SetForegroundWindow`는 Windows가 자주 거부한다(포커스 훔치기 방지). 앞으로 가져와야만 되는 동작은 설계에서 뺀다.
메시지는 백그라운드 창에도 보낼 수 있으니, 포커스가 필요 없는 길을 먼저 찾는다.

## 6. Enter가 줄바꿈이 되거나 전송이 된다

앱 설정(Enter로 전송 / Ctrl+Enter로 전송)에 따라 다르다. 보낸 뒤 반드시 다시 읽어 새 항목이 생겼는지,
입력창이 비었는지 본다. 둘 다 아니면 `outcome_unknown`이고 다시 보내지 않는다.

## 7. 고해상도(DPI) 좌표

휠 메시지처럼 좌표가 들어가는 메시지는 `GetWindowRect` 값이 DPI 가상화로 어긋날 수 있다.
헬퍼 시작 시 `SetProcessDpiAwarenessContext(-4)`(Per-Monitor V2)를 시도하고, 좌표 의존 동작은 최소화한다.

## 8. 앱 업데이트로 클래스 이름이 바뀐다

창 클래스 · AutomationId는 공개 약속이 아니다. 찾지 못하면 추측해서 비슷한 요소를 누르지 말고
`*_not_found`로 멈춘 뒤 덤프를 다시 뜬다.
